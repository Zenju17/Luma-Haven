# Row-level security

Live inspection found RLS disabled and no public policies; table owner and inspection role are postgres. The deployed Django and worker roles and Data API exposure remain unverified. No RLS security is claimed and no policies are added. Current Django staff queries are global, so tenant isolation is not implemented either. Do not introduce separate customer properties under this design.

Phase in a non-owner, non-BYPASSRLS runtime role separate from migration/admin roles; inventory grants and disable or restrict unneeded Data API access. Establish validated user, organization, property and permission context inside each transaction using `SET LOCAL`/`set_config(..., true)` before any query. Explicitly fail closed when context is absent, and ensure atomic request boundaries and worker job context; transaction end clears local settings. Pooling, retries, asynchronous tasks, migrations, admin and management commands need explicit audited contexts. Define separate SELECT/INSERT/UPDATE/DELETE policies and restrictive financial/audit deletion, then test with the actual runtime role including cross-property reads and writes, missing context and connection reuse. Migrations use a separately controlled owner role and operational bypass is audited. RLS is defense in depth, not a replacement for application authorization.
